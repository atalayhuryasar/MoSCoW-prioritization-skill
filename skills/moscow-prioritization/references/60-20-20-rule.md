# The 60/20/20 Rule in MoSCoW Prioritization

The **60/20/20 Rule** provides the mathematical backbone for realistic Agile delivery. Without quantitative constraints, MoSCoW often collapses under political pressure into a backlog where 90% of features are designated "Must Have".

---

## Capacity Allocation Table

| Category | Target Effort Share | Tolerable Range | Role in Delivery |
|---|---|---|---|
| **Must Have** | $\le 60\%$ | $40\% - 60\%$ | Guarantees the baseline MVP and core value proposition. |
| **Should Have** | $\sim 20\%$ | $15\% - 25\%$ | Delivers high-impact value; adjustable if velocity drops. |
| **Could Have** | $\sim 20\%$ | $15\% - 25\%$ | The contingency buffer; sacrificed first if obstacles arise. |
| **Won't Have** | $0\%$ | $0\%$ | Parked for future sprints; shields the team from scope creep. |

*Note: Percentage is calculated strictly against in-scope effort ($\text{Must} + \text{Should} + \text{Could}$). Deferred "Won't Have" items are excluded from the 100% active budget.*

---

## Why 60%? The Mathematics of Delivery Risk

1. **Uncertainty & Discovery:** In real-world software engineering, unexpected technical debt, edge cases, integration hurdles, and requirement refinements consume approximately 20–30% of sprint time.
2. **Predictable Commitments:** By committing to only 60% of work as mandatory, a team can guarantee **100% on-time delivery** of its critical promise, even when negative variance strikes.
3. **The 40% Shock Absorber:** The combined 40% of Should (~20%) and Could (~20%) acts as a shock absorber:
   - If velocity is higher than expected: Team ships Must + Should + Could.
   - If velocity is normal: Team ships Must + Should + some Could.
   - If an outage or crisis occurs: Team safely drops Could and defers some Should, but **still ships all Musts on time**.

---

## Warning Signs (Red Flags)

| Warning Sign | Metric Indicator | Consequence & Action |
|---|---|---|
| 🚨 **Must-Heavy Backlog** | $\text{Must} > 60\%$ | High risk of delivery crunch or missed deadline. **Action:** Demote lowest-impact Must items to Should. |
| ⚠️ **Zero Buffer** | $\text{Could} < 10\%$ | Any minor setback will force immediate compromise on Should or Must. **Action:** Carve out low-cost Could items. |
| ⚠️ **All or Nothing** | $\text{Should} > 35\%$ | Team is reluctant to make hard choices between essential and desirable. **Action:** Re-evaluate workarounds. |
| ⚠️ **Unestimated Scope** | Items lacking points | Percentages are meaningless without sizing. **Action:** Run relative sizing exercise before final categorization. |

## Using the CLI Validator Tool

The repository provides an automated script to validate your effort distributions.

### Input JSON Structure (`input.json`)
```json
{
  "project": "E-Commerce Checkout",
  "items": [
    { "name": "Credit Card Processing", "category": "must", "effort": 8 },
    { "name": "Apple Pay Integration", "category": "should", "effort": 3 },
    { "name": "Gift Card Balance Checker", "category": "could", "effort": 3 },
    { "name": "Cryptocurrency Payments", "category": "wont", "effort": 13 }
  ]
}
```

### Running Validation
```bash
python scripts/validate_moscow.py examples/input.json
```
